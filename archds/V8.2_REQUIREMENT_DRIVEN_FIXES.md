# ARCHDS V8.2 — Requirement-Driven Reliability Fixes

## Fixed
- UML use-case generation now excludes pure quality/NFR statements from user goals and derives concise actions from functional requirements.
- UML actors use a dedicated vertical rail so actor labels and association connectors do not overlap.
- UML domain classes are derived from explicit business concepts in functional requirements; architecture infrastructure and quality-attribute fragments are not converted into classes.
- UML class relationships are created only from concepts that co-occur in the same submitted functional requirement.
- Sequence diagrams use only the selected functional requirement and components explicitly mapped to that requirement. Unrelated architecture components are no longer appended just because they exist in the graph.
- Sequence message labels are derived from the requirement/component evidence instead of the generic hardcoded `Process requirement-driven operation` label.
- Final Decision now initializes to a real candidate ID, validates it against the returned candidates, and sends the candidate key expected by the backend. This fixes `candidateId must not be blank`.
- Ask ARCHDS now has a requirement-aware deterministic reasoning fallback for broad question categories (requirements, risks, scale, security, cost, alternatives, production readiness and arbitrary questions). If `LLM_API_KEY` is configured, the existing OpenAI-compatible provider can enrich the answer; without a key, ARCHDS still returns evidence-grounded answers instead of a generic empty response.
- Digital Twin scenarios remain generated from the submitted requirement profile and selected candidate. Scenario simulations produce different metric deltas, affected components and mitigation proposals based on scenario type, intensity, scale and candidate topology.
- PDF generation has a valid-PDF fallback in the AI report service, explicit PDF validation in the backend/frontend, and the AI service timeout is increased to 180 seconds for large analysis payloads.

## Validation
- Python compilation: passed.
- AI service tests: 13/13 passed.
- Requirement-specific UML smoke test: passed; no NFR-only use cases and no unrelated sequence components.
- Digital Twin smoke test: different requirement-grounded scenarios produced different metrics/affected components/actions.
- PDF smoke test: generated valid `%PDF-1.4` output.

## Important
The architecture engine contains rule-based domain vocabulary and architectural pattern heuristics. These are decision rules, not demo-system answers. Runtime architecture, diagrams, explanations, scenarios and decision evidence are generated from the submitted requirements and selected candidate.
