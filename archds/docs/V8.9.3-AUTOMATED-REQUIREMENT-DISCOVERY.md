# ARCHDS V8.9.3 — Automated Requirement Discovery and Scoring

## User input contract
The default workflow requires only a project title and a short natural-language description. The advanced section is optional. Functional requirements, NFRs, workload numbers, budget, technology preferences, and objective priorities are not required to start a first-pass analysis.

## Requirement analysis
The requirement analyst classifies natural-language sentences using business-action and quality-attribute signals, adds conservative domain defaults for healthcare, commerce, finance, recruitment, campus/education, and IoT contexts, and adds a small engineering baseline for maintainability, observability, input validation, and failure handling. Inferred items are recorded as assumptions for human review. The extraction is a transparent heuristic, not a guarantee of complete natural-language understanding.

## Technology recommendation policy
- Structured transactional business records: PostgreSQL is the default system-of-record recommendation when no database preference is supplied.
- Explicit database/framework choices take precedence over inferred defaults.
- Redis is recommended only when scale, latency, read-heavy, or bursty workload signals justify a cache. Cache-aside, TTLs, and invalidation safeguards are documented.
- RabbitMQ is recommended for ordinary asynchronous business workflows such as notifications and background jobs.
- Kafka is recommended for high-volume event streams or telemetry workloads.
- React is the default interactive browser UI. Spring Boot is preferred by the deterministic rule set for enterprise/transactional domains; FastAPI is preferred for ML/analytics-oriented services. These are explainable defaults, not universal best choices.
- Rate limiting/admission control and horizontal scaling/load balancing are added when scale or burst signals are detected.
- Dead-letter queues, bounded retries, and idempotency controls are added when a message broker is recommended.

## Who supplies the score?
Users do not enter candidate scores. The evaluator computes candidate dimension scores from a deterministic rubric: an architecture-pattern baseline is adjusted using detected drivers and implemented controls, then combined using objective weights. Objective weights are inferred from requirements by default. Optional custom priorities can influence the inferred weights by 25%, but they are not candidate scores. Specialist reviewers produce findings, the Pareto module identifies non-dominated candidates, and the decision judge considers constraint violations, critical findings, Pareto status, requirement coverage, and weighted score.

## Important research limitation
This implementation is an explainable, rule-based decision-support method with modular specialist agents; it is not a trained model proven optimal on every domain. Scores are comparative heuristics and should be calibrated against expert-labelled examples before being interpreted as empirically validated quality measurements. Numeric workload targets and availability SLAs should be confirmed when they materially affect deployment choices.

## Verification
The AI-service suite includes 15 tests, including tests for minimal-input analysis, requirement-derived weights, concrete technology selection, technology preference preservation, and connected traffic-mitigation components. Execute `python -m pytest -q` from `ai-service` to reproduce the service tests. The frontend production build and Maven verification must be run in an environment with frontend dependencies and Maven installed.
